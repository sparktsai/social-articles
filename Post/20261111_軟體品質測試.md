# AI 時代的軟體品質測試

## 問題的起點

1. 過去以為 Vibe Coding 產生的程式即使所有測試都通過，仍不代表實際可用，主要是因為測試往往只覆蓋 UI 操作與少數端到端的 Happy Path，沒有充分驗證例外情境、資料邊界及真實執行環境。
2. 後來想，如果把非功能需求（Non-functional Requirements）也納入規格，或者在規格驅動開發（Specification-Driven Development, SDD）中加入測試規格，是否就能對 AI 產生的程式碼提供品質保證？
3. 在整理 Edge Case 相關文章時發現：AI 雖然可以列出常見的邊界與異常案例，但若沒有提供完整的業務規則、資料限制、風險模型及歷史事故，它通常只能產生可由現有上下文推導的測試，無法證明重要情境已被完整覆蓋。

## 重新整理軟體測試

### 測試層級

常見的測試層級包括：

- 單元／元件測試（Unit／Component Testing）：驗證單一函式、類別或元件。
- 元件整合測試（Component Integration Testing）：驗證元件之間的互動。
- 系統測試（System Testing）：驗證完整系統的功能與非功能特性。
- 系統整合測試（System Integration Testing）：驗證系統與其他系統、外部服務之間的介面。
- 驗收測試（Acceptance Testing）：確認系統是否符合業務需求，並具備部署或交付條件。

端到端測試（End-to-End Testing, E2E）則是從使用者或業務流程的起點一路驗證到終點。它可能跨越完整系統及外部服務，但不等同於系統測試或驗收測試。

### 測試類型

測試層級回答的是「在哪一層測」，測試類型回答的則是「要驗證什麼」。

- 功能測試：功能是否完整、正確並符合用途。
- 非功能測試：系統表現得有多好，例如效能、安全性、可靠性、可用性、相容性及可維護性。
- 結構性測試：程式內部結構及路徑是否被適當覆蓋。
- 變更相關測試：修正後的確認測試與迴歸測試。

非功能需求不能只寫「效能良好」或「系統必須可靠」，而應該轉換成可量測的條件，例如：

- 95% 的 API 請求須在 300 ms 內完成。
- 故障後的服務復原時間（RTO）不得超過 15 分鐘。
- 使用者只能讀取所屬租戶的資料。
- 10,000 個併發連線下，錯誤率須低於 0.1%。

把需求寫進規格，不等於需求已經被驗證；還需要合適的環境、資料、工具與通過門檻。

### 測試文件與驗收條件

在我過去參與的專案中，曾使用 QTR（Qualification Test Report）、ATR（Acceptance Test Report）等正式測試報告。採用 Agile 後，日常開發較常以 Acceptance Criteria 描述一項需求何時算完成，但這不表示 Acceptance Criteria 取代了測試報告。

兩者用途不同：

- Acceptance Criteria 是需求的完成及驗收條件。
- Test Report 是測試執行結果、涵蓋範圍、缺陷與風險的證據。

在受法規、合約或稽核要求約束的 Agile 專案中，仍然需要保留正式的測試紀錄與報告。

### 測試驅動方法與測試技法

TDD、ATDD 與 BDD 不是依序互相取代的演進，而是關注不同問題、可以搭配使用的方法：

- TDD（Test-Driven Development）：先寫失敗測試，再完成最少實作並重構。常見於單元或元件層級，但不限於此。
- ATDD（Acceptance Test-Driven Development）：在開發前由業務、測試與開發共同定義驗收範例，不等同於 E2E 測試。
- BDD（Behavior-Driven Development）：以共同的領域語言描述系統行為，促進業務與技術角色協作。Given–When–Then 是常見格式，但不是 BDD 的全部，也不限於 E2E 測試。

另外還有可用於不同層級的測試技法：

- Contract Testing：驗證服務之間交換的請求、回應或訊息是否符合共同契約。若由消費者需求定義契約，通常稱為 Consumer-Driven Contract Testing（CDC）。
- Data-Driven Testing（DDT）：使用多組輸入與預期結果重複執行相同測試，可應用於單元、API、整合及 E2E 測試。
- 邊界值分析、等價類別劃分、決策表與狀態轉移測試：用來有系統地找出只靠範例容易遺漏的情境。

## AI 時代的額外風險

AI 可以產生程式碼，也可以產生測試，但「程式與測試都由 AI 完成」不會自動形成獨立的品質保證。

如果同一個 AI Agent 同時擁有修改實作與測試的權限，它可能為了讓測試通過而：

- 降低斷言強度，甚至只確認程式沒有拋出錯誤。
- 刪除或改寫失敗案例，使測試配合錯誤的實作。
- 以過度簡化的 Mock 取代真實整合。
- 只驗證自己產生的資料與情境，忽略真實世界的髒資料、競態條件及環境差異。

Mock 本身不是問題。它是隔離相依性、提高速度與穩定性的正常測試技術。真正的風險是只有 Mock，卻沒有契約驗證、真實資料庫測試或較高層級的整合測試，導致 Mock 的行為與正式環境不一致。

### 測試預言問題

測試只能證明實作符合測試所描述的預期；如果預期結果本身錯誤或不完整，所有測試通過仍然不能證明產品正確。

當需求、實作與測試都是由同一個 AI 根據同一份不完整的上下文產生時，它們可能一致地犯下相同錯誤。例如，規格漏掉跨租戶存取限制，AI 產生的程式與測試也可能一起漏掉，最後得到「全部通過」但存在資安漏洞的結果。

## 如何確保 AI 產生軟體的品質

軟體品質至少包含三個面向：

1. 功能正確性（Functional Correctness）：功能是否依規格做對。
2. 非功能品質（Non-functional Quality）：效能、安全性、可靠性、可用性及可維護性是否符合要求。
3. 適用性（Fitness for Purpose）：產品是否真的解決使用者與業務的問題。

因此，不能讓 AI 同時擔任需求來源、實作者、測試設計者與最終裁判。實務上可以建立下列防線：

- 由人確認需求、風險與不可違反的業務規則。
- 將功能與非功能需求寫成可觀察、可量測的驗收條件。
- 除了 Happy Path，也使用風險導向及系統化的測試設計技法。
- 將關鍵驗收測試、資安規則及品質門檻與實作 Agent 隔離，避免被任意修改。
- 同時保留快速的 Mock 測試、契約測試，以及使用真實相依服務的整合測試。
- 使用與正式環境相近的資料與環境進行 E2E、效能、安全性及可靠性測試。
- 對 AI 修改測試、降低斷言或更新基準結果的行為進行人工審查。
- 以程式碼審查、靜態分析、依賴與弱點掃描、執行期監控及漸進式發布補足自動化測試的盲點。

AI 可以協助擴大測試範圍與加快回饋，但不能單獨證明軟體品質。品質保證的關鍵，不是增加更多由同一個 AI 推導出的測試，而是建立獨立的品質依據、驗證機制與發布門檻。
