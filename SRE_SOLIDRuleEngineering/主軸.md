# SOLID 從 Human 到 AI：文章主軸

## 文件定位

這份文件定義文章的核心論述，不討論特定 Skill、工具或產品。

主題聚焦三個問題：

1. SOLID 為什麼在物件導向軟體發展中出現？
2. AI Generate Code 如何改變 SOLID 面對的問題與地位？
3. SOLID for Human 轉向 SOLID for AI 時，必須增加什麼？

---

## 核心主張

> SOLID 的目的不是讓程式符合五種結構形式，而是提高軟體面對需求變動時的可維護性。

傳統 SOLID 預設人類先理解需求，再使用設計原則組織程式。

AI Generate Code 卻容易反過來：模型先讀取或產生程式，再從程式結構推測責任、變動與設計意圖。

因此，SOLID 在 AI 時代的轉變，不是增加更多 Code Rules，而是讓 Requirement、Change Driver 與 Design Rationale 成為 AI 可以取得、區分與驗證的 Context。

---

## 整體論述路徑

```text
需求持續變動
    ↓
軟體需要可維護性
    ↓
OO 提供組織責任、狀態與協作的方式
    ↓
RUP 連接 Use Case、Architecture、Iteration 與 Risk
    ↓
SOLID 限制需求變動造成的修改擴散
    ↓
AI 大幅提高 Code Generation 的速度與數量
    ↓
程式推論開始取代需求語意推論
    ↓
產生過度設計、功能過大與無根的變動性
    ↓
SOLID 必須從 Human Design Principle
轉為 Human–AI Requirement–Design Alignment Principle
```

---

## 主軸一：SOLID 的歷史起點不是五個字母

SOLID 不應從五項原則的定義直接講起。

它的問題背景是：軟體會隨需求修改而逐漸變得難以理解、難以變更，並產生修改擴散、破壞與重用困難。

因此，歷史論述應先回答：

- 物件導向試圖解決什麼問題？
- Architecture 如何承受需求與風險？
- 為什麼軟體經過多次修改後會逐漸腐化？
- SOLID 如何回應可維護性問題？

### OO 的位置

物件導向提供建立軟體邊界的語言：

- Object 結合狀態與行為；
- Encapsulation 隱藏內部決策；
- Abstraction 提供穩定的使用邊界；
- Polymorphism 允許不同實作維持共同契約；
- Responsibility 決定哪個物件應該知道或執行什麼。

OO 可以建立邊界，卻不保證邊界一定正確。

Class 仍可能混合不同需求；Inheritance 仍可能破壞替換契約；Interface 也可能綁定不相關的 Client。

### RUP 的位置

RUP 將數個重要觀念連接起來：

- Use-case driven；
- Architecture-centric；
- Iterative and incremental；
- Risk-driven。

Use Case 連接 Actor Goal 與系統行為；Architecture 支撐重要需求與風險；Iteration 則承認需求與設計會在實作中持續被釐清。

SOLID 並非源自 RUP，兩者也不是同一層次的方法。

它們的共同問題是：

> 軟體如何在需求持續改變時，維持可理解、可修改與可驗證？

---

## 主軸二：SOLID 的目的是可維護性

SOLID 不是程式碼美學，也不是五項獨立的格式規則。

它們可以放回同一個問題理解：

> 當需求改變時，系統能否以合理成本完成修改，而不讓影響不必要地擴散？

可維護性不只是程式容易閱讀，也包含：

- 能找到應該修改的位置；
- 能理解修改的業務理由；
- 能限制修改影響範圍；
- 能保留既有契約與行為；
- 能獨立測試受影響的部分；
- 能新增合理變體而不破壞穩定核心；
- 能判斷哪些行為應該一起改變，哪些不應互相影響。

### 五項原則與變動的關係

- **SRP**：不要讓不同 Actor、Policy 或 Requirement 的變動集中修改同一單元。
- **OCP**：面對已證實且會反覆發生的變動軸，新增變體不應持續破壞穩定核心。
- **LSP**：替換實作時，不應破壞呼叫端依賴的需求契約。
- **ISP**：不同 Client 的需求不應被綁在同一份過大的 Interface。
- **DIP**：穩定的高階政策不應被易變的技術細節控制。

五項原則的共同目的，是讓不同需求造成的變動保持相對獨立。

---

## 主軸三：可維護性來自需求變動

如果不知道系統會因什麼原因改變，就無法可靠判斷什麼設計比較容易維護。

Change Driver 可能來自：

- 不同 Actor 或 Stakeholder；
- 不同 Business Policy；
- 不同法規或合規要求；
- 不同資料來源或外部系統；
- 不同失敗、補償與一致性要求；
- 不同效能、安全性或可靠性需求；
- 不同 Ownership 與 Release Cadence；
- 已知即將加入的產品變體。

因此：

```text
Requirement Source
    ↓
Change Driver
    ↓
Responsibility / Variation Boundary
    ↓
Package / Class / Interface / Method
```

SOLID 判斷不應只從最後一層的程式結構開始。

---

## 主軸四：AI Generate Code 改變的是生產方式，不是需求變動

AI 沒有消除需求變動。

它改變的是：

- 程式碼產生速度；
- 一次產生的程式碼規模；
- 產生者對完整系統的熟悉程度；
- Code Review 的供需比例；
- 設計決策被形成與保存的方式；
- 後續維護時能取得的 Context。

### 傳統開發

```text
理解需求
→ 建立設計模型
→ 逐步撰寫程式
→ 在實作中修正理解
```

### AI Generate Code

```text
輸入需求描述
→ AI 補全缺少的語意
→ 快速產生完整實作
→ 人類看到的是生成結果
```

程式碼產量提高，但需求理解與設計判斷不一定同步增加。

新的瓶頸會從「如何寫出 Code」轉向：

- 如何判斷設計是否對應需求？
- 如何驗證 AI 補全的語意？
- 如何保存邊界存在的理由？
- 如何讓後續 Human 或 AI 能安全修改？

---

## 主軸五：程式推論與需求語意推論

這是分析 AI Generate Code 問題的核心區分。

### 程式推論

程式推論觀察：

- Branch；
- Dependency；
- Call Graph；
- Duplicate Code；
- Method 大小；
- Interface 與 Inheritance；
- 現有 Test 與 Caller。

它可以回答：

- 程式現在如何組成？
- 哪些單元互相依賴？
- 修改 Signature 會直接影響哪些 Caller？
- 哪些路徑目前執行不同操作？
- 哪些程式在語法上相似？

但它不能單獨證明：

- Branch 代表不同 Business Policy；
- 相似 Function 會因相同需求而改變；
- Concrete Dependency 需要被替換；
- 大型 Method 包含多個責任；
- 某個未來變體值得預先建立 Extension Point。

### 需求語意推論

需求語意推論尋找：

- 誰會要求改變？
- 為什麼需要改變？
- 哪一項 Policy 會改變？
- 哪些行為必須一起改變？
- 哪些行為應該彼此獨立？
- 哪些契約必須保持不變？
- 哪些變動已有證據，哪些只是想像？

它的證據來自：

- Actor 與 Stakeholder Goal；
- Use Case；
- Acceptance Criteria；
- Business Rule；
- Quality Attribute；
- Regulatory Constraint；
- Change Scenario；
- Requirement History。

核心差異是：

> 程式推論能發現可能的結構訊號；需求語意推論才能確認變動的來源。

---

## 主軸六：程式推論為什麼容易過度

LLM 擅長從可見 Pattern 延伸可能解釋。

```text
存在 Branch
→ 存在多個變體
→ 未來還會增加變體
→ 應建立 Strategy

存在多個 Dependency
→ 存在多個責任
→ 應拆成多個 Service

存在相似程式碼
→ 代表同一概念
→ 應建立共同 Abstraction
```

第一步可能是 Code Fact，後續步驟卻已跨越到未經需求支持的 Semantic Inference。

問題不是 AI 使用推論，而是模型可能沒有清楚標示：

- 哪裡是可觀察事實；
- 哪裡開始推測需求；
- 哪些資訊目前不存在；
- 哪個結論需要人類確認。

---

## 主軸七：無根的變動性

SOLID 設計經常使用這些說法：

- 這裡可能改變；
- 這裡需要擴充；
- 這裡應該可替換；
- 這裡需要隔離變動；
- 這裡需要一個抽象。

每一項變動性都應該可以追問：

> 它來自哪一項 Requirement、Actor、Policy、Constraint 或已知 Change Scenario？

### 有根的變動性

```text
Requirement / Actor / Policy / Change Scenario
    ↓
Change Driver
    ↓
Responsibility 或 Variation Boundary
    ↓
程式設計
```

### 無根的變動性

```text
Branch / Dependency / Similar Code / Large Method
    ↓
推測未來可能改變
    ↓
建立 Abstraction 或拆分
    ↓
找不到 Requirement Source
```

無根的變動性會形成 Speculative Generality：系統為沒有證據的未來，先付出當下的複雜度。

## 主軸八：Code-first 會造成兩個相反的極端

### False Split：過度設計

看到大型 Method、Branch、Dependency 或相似程式碼，就直接建立：

- Interface；
- Factory；
- Strategy；
- Service Layer；
- Extension Point；
- 共用 Abstraction。

如果抽象沒有對應真實 Change Driver，就可能造成：

- 過多概念與檔案；
- 更高的間接呼叫成本；
- 業務流程被 Pattern 隱藏；
- 修改簡單行為也需要跨越多層；
- 預測錯誤時，抽象比原始程式更難修改。

### False Cohesion：功能過大

每次加入需求時，都把新 Branch、Dependency、Side Effect 與 Exception 放入最接近的既有 Function。

長期可能形成：

- God Function；
- God Class；
- 依 Flag 切換不同業務目的的 Method；
- 同時處理 Policy、Persistence、Formatting 與 Notification 的流程；
- 不同 Actor 的需求集中修改同一單元。

False Split 與 False Cohesion 看似相反，根因卻相同：

> 只有程式結構，沒有需求語意與變動來源。

## 主軸九：SOLID for Human 與 SOLID for AI

這是全文最重要的轉折。

### SOLID for Human 的隱含前提

傳統 SOLID 預設人類設計者能夠：

- 與 Stakeholder 討論需求；
- 理解業務背景；
- 知道過去的設計決策；
- 辨識可能的變動原因；
- 對模糊資訊提出問題；
- 記得團隊接受的 Trade-off；
- 在原則衝突時作出情境判斷。

因此，「一個 Class 應該只有一個變動原因」可以保持高度濃縮。

傳統 SOLID 預設「Reason to change」由人類理解。

### SOLID for AI 缺少的前提

AI 只能使用當次 Context 中可取得的：

- Prompt；
- Code；
- Test；
- Issue；
- 文件；
- Current Diff；
- Repository 內可搜尋的資訊。

如果設計理由存在於人類記憶、會議、Chat 或未被載入的文件，對當次 AI 而言，這些知識實際上不存在。

AI 看到「one reason to change」時，可能只能從 Code Shape 猜測 Reason。

### 關鍵差異

| 面向 | SOLID for Human | SOLID for AI |
|---|---|---|
| 語意來源 | 人類理解需求與業務背景 | 受限於當次可取得的 Context |
| Change Driver | 可由溝通、經驗與組織知識辨識 | 必須明確提供或標示為推論 |
| 原則用途 | 引導人類的設計判斷 | 同時約束模型推論與生成行為 |
| 面對模糊 | 可以詢問、討論並承擔判斷 | 容易自行補全缺少的語意 |
| 設計記憶 | 存在人員與團隊的長期記憶 | 不一定跨 Session 或 Agent 保留 |
| 常見偏差 | 受經驗、時間與個人偏好影響 | 容易依常見 Pattern 過度一般化 |
| 維護對象 | 主要服務下一位人類 | 同時服務 Human 與下一個 AI |
| 核心產物 | 可維護的 Code Structure | Code Structure 加上可取得的 Semantic Context |

### 兩者的公式

```text
SOLID for Human
= Design Principles
+ Human Semantic Judgment
```

```text
SOLID for AI
= Design Principles
+ Accessible Requirement Context
+ Bounded Inference
+ Traceable Evidence
+ Explicit Uncertainty
```

這不是說 Human 一定理解需求、AI 一定無法理解需求。

真正差異是：

> 人類可以透過組織參與、經驗與持續溝通取得大量未文件化的語意；AI 的判斷更直接受限於當次可存取的 Context。

因此，SOLID for AI 必須將過去依賴人類內隱知識的部分外顯化。

## 主軸十：AI Maintain Code 與語意侵蝕

AI 維護既有程式碼時，通常從設計結果反推設計原因。

```text
原始需求與設計理由
    ↓
目前程式結構
    ↓
AI 從程式反推語意
    ↓
AI 依推測重新拆分、合併或抽象
```

一次推論偏差會成為下一次維護的新依據：

```text
缺少原始語意
→ Agent A 依 Code 推測責任
→ 產生不適當拆分或合併
→ Agent B 把新結構視為既有設計意圖
→ 建立更多 Dependency、Test 與 Abstraction
→ 偏差逐步固化
```

程式可能仍然通過測試，但 Requirement 與 Code 的對應會逐步漂移。

這種現象可以稱為「語意侵蝕」。

---

## 主軸十一：測試通過不代表設計語意被保存

測試通常可以證明選定輸入仍得到選定結果，卻不一定記錄：

- 為什麼兩個 Function 必須分離；
- 為什麼某些步驟必須位於同一個 Transaction；
- 哪個 Stakeholder 擁有某項 Policy；
- 為什麼當初刻意沒有建立共用抽象；
- 哪些未來變動不應影響目前核心。

因此，AI 可以在所有 Test 通過的情況下，破壞 Responsibility Boundary、Substitution Contract 或 Dependency Policy。

功能沒有立即失效，但下一次需求修改會變得更廣、更難與更危險。

這就是可維護性的退化。

## 主軸十二：SOLID 在 AI 時代的新地位

SOLID 不會因 AI 能產生程式碼而過時。

AI 反而放大了 SOLID 原本處理的問題：

- 修改影響是否擴散？
- 責任是否混合？
- 抽象是否對應真實變體？
- 替換是否維持需求契約？
- 高階政策是否受到技術細節控制？

但 SOLID 的地位需要改變。

### 過去：Human Coding Guideline

```text
Human 理解需求
→ Human 進行設計
→ SOLID 協助組織 Code
```

### 現在：AI Generation Constraint

```text
需求描述
→ AI 推論設計
→ SOLID 限制產生的程式結構
```

### 應有的轉變：Requirement–Design Alignment Principle

```text
需求語意
→ Change Driver
→ Responsibility / Variation Boundary
→ 程式結構
→ 持續驗證兩者是否對應
```

SOLID 不應只存在於 Code Review 的最後階段，而應進入需求、設計、生成與維護之間。

## 主軸十三：SOLID 應該發生的轉變

### 從 Code-first 轉向 Requirement-first

不只問：

> 這個 Class 是否有太多 Method？

而要問：

> 這個 Class 是否同時承擔由不同需求來源驅動的政策？

### 從 Structure Compliance 轉向 Change Traceability

不只檢查是否使用 Interface，而要追問：

> 這個 Interface 隔離的是哪一種已知變動？

### 從原則宣告轉向推論透明

設計判斷需要區分：

- Code Fact；
- Requirement Fact；
- Semantic Inference；
- Missing Context。

### 從避免大型程式轉向避免錯誤邊界

真正需要避免的是：

- 把不同 Change Driver 放在同一邊界；
- 把同一項一致性責任拆散；
- 為沒有需求根據的未來建立抽象。

### 從 Human-readable 轉向 Human-and-AI-legible

未來可維護性同時包含：

1. **Human Legibility**：人類能理解 Code 與設計。
2. **Agent Legibility**：AI 能取得 Requirement、Constraint 與 Boundary Rationale。

### 從「寫出好 Code」轉向「保存設計理由」

AI 可以重新產生 Code，但如果 Design Rationale 遺失，新的 Code 只能重新猜測需求。

未來更稀缺的資產可能不是程式碼，而是：

- Requirement Context；
- Architecture Decision；
- Change Driver；
- Boundary Rationale；
- Accepted Trade-off。

## 最終結論

> SOLID for Human 假設人類先理解需求，再使用原則設計程式。

> SOLID for AI 容易先讀取程式，再從結構推測需求與變動。

因此，AI 時代的 SOLID 不能只檢查程式是否具有某種結構。

它必須持續確認：

- Responsibility 是否有 Requirement Source；
- Variation Point 是否有真實 Change Driver；
- Abstraction 是否隔離已知變動；
- 程式邊界是否仍與需求語意相符；
- 缺少 Context 時是否誠實保留不確定性。

SOLID 過去主要保護程式碼，避免需求變動造成失控。

SOLID for AI 還必須保護需求語意，避免它在程式生成與反覆維護中被模型重新解釋。
